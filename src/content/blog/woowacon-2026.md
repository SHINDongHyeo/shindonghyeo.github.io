오늘 우아한형제들이 주최한 기술 컨퍼런스 우아콘 2026에 다녀왔다. 키노트를 포함해 7개 세션을 들었는데, 5개는 AI 활용 사례였고 2개는 주문·재고처럼 정확해야 하는 시스템을 다룬 백엔드 이야기였다. 들으면서 적은 메모를 세션별로 정리하고, 중간중간 든 생각도 같이 남긴다.

> 세션 제목은 공식 제목이 아니라, 내용을 보고 내가 붙인 것이다.

## 한눈에 보기

| 트랙 | 주제 | 한 줄 요약 |
| --- | --- | --- |
| 키노트 | AI로 배달 경험 개선 | 조리·도착 시간을 과거 데이터로 예측하고, 예측 → 결과 확인 → 개선을 반복한다 |
| D | AI로 기술 블로그 검수 | Claude 스킬로 글쓴이의 개성은 지키면서 검수 규칙을 적용했다 |
| A | Temporal 워크플로우 엔진 | 서버마다 흩어진 큐·리스너를 중앙에서 관리하는 구조로 바꿨다 |
| E | CS 인입량 예측 | 시계열 파운데이션 모델에 사내 데이터와 강수량·휴일 정보를 더했다 |
| D | 사내 바이브코딩 툴 | 만드는 것보다 신뢰·홍보·유지보수가 더 어렵다 |
| D | AI 장애 분석 | 실행은 코드가, 판단은 LLM이 맡도록 역할을 나눴다 |
| E | 퀵커머스 통합 | B마트와 배민스토어의 카탈로그·가격·재고를 하나로 합쳤다 |

AI 세션들에서는 AI에게 그냥 맡기지 않고 성공 기준, 관련성 검증, 소규모 베타 테스트처럼 결과를 믿을 수 있게 만드는 장치가 반복해서 나왔다.

## 키노트 · AI로 배달 경험 개선하기

배민은 사람이 직접 입력하거나 수동으로 관리하던 값을 AI 예측으로 바꾸고 있다. 방향은 'AI로 예측 → 결과 확인 → AI 개선'을 계속 반복하는 것이다.

- **조리시간**: 직접 입력하던 조리시간을 기존 데이터로 더 정확하게 추정한다. 부정확하게 입력된 정보도 바로잡을 수 있다.
- **비 올 때 배달 가능 범위**: 예전에는 관리자가 수동으로 범위를 고쳤다. 이제는 AI로 빠르게 처리한다.
- **기다리는 시간 단축**: 이전 데이터를 학습해 조리시간·도착시간 등을 더 빠르고 정확하게 예측하고, 고객이 기다리는 시간을 줄인다.

## D트랙 · AI로 기술 블로그 글 검수하기

배민에는 기술 블로그 글의 검수와 발행을 맡는 '테크니컬 라이팅 코치'가 따로 있다. 코치가 글을 읽고 고칠 부분을 짚어 주던 일을 AI로 처리하는 것이 목표였다.

- **스킬은 개성을 지켜준다**: Claude 스킬로 수정하니, 글쓴이가 일부러 넣은 비유법 같은 개성은 그대로 남았다. 모델 성능에만 기대기보다 스킬로 정확한 지침을 주는 편이 낫다.
- **적용과 탐지를 나눴다**: 규칙만 넣었더니 잘 지키지 않았다. 그래서 '규칙 적용'과 '규칙 위반 탐지'를 별도 스킬로 만들어 따로 돌렸다.
- **가상 독자**: Nemotron-Personas-Korea로 한국인 페르소나 100명을 만들어 봤다.
- **공개 예정**: 이 테크니컬 라이팅 스킬을 우아한형제들 기술 블로그에 공개할 예정이다.

**내 생각**

- 적용과 탐지를 굳이 스킬 두 개로 나눌 필요가 있을까? 한 스킬 안에 "먼저 이것을 하고, 마지막에 이것을 점검하라"처럼 순서를 적어 주면 해결될 것 같다.
- AI에게는 명확한 성공 기준을 주는 게 좋다(Anthropic 공식 문서에도 나온다). "좋은 문장 써 줘"가 아니라 "이 기준으로 높은 점수가 나오게 써 줘"처럼 맡길 수 있어야 한다.

## A트랙 · Temporal로 서버 간 흐름 한곳에서 관리하기

서버마다 제각각이던 큐·리스너 구조를 Temporal 워크플로우 엔진으로 모아, 장애 분석과 복구를 쉽게 만든 이야기다.

**도입 배경**

- 장애가 나면 로그를 뒤져 분석했는데, 이 과정이 너무 힘들었다.
- 여러 서버가 각자 자신만의 큐나 리스너 구조로 동작해 흐름이 복잡했다.

Temporal은 여러 서버가 통신할 때 거치는 '중앙 관제소' 같은 역할을 한다.

**장점**

- **Replay**: 워커1이 죽어도 그 전까지의 실행 기록이 모두 남는다. 워커2가 이 기록을 받아 처음부터 따라가며 상태를 되살린 뒤, 죽은 시점부터 일을 이어서 한다.
- **외부 장애에 덜 흔들린다**: 외부 API 장애에 대비한 재시도·타임아웃 설정을 엔진이 제공해 편리하다.

**겪은 문제와 해결**

| 문제 | 해결 |
| --- | --- |
| DB I/O 부하 | 클러스터를 늘려 해결했다. 결국 DB 자체를 증설한 것으로 보인다. |
| 시그널 핸들러 관리 | Temporal로 들어오는 시그널을 처리하는 핸들러를 한 메서드에 모았다. 주문부터 배달 완료까지 과정을 순서대로 나열해 흐름이 한눈에 보이게 했다. |

## E트랙 · 시계열 파운데이션 모델로 CS 인입량 예측하기

CS 상담사는 서버처럼 자동으로 늘릴 수 없어서, 문의가 언제 몰릴지 미리 예측했다. 예측 결과는 상담사 수를 조정하는 데 쓰는 것으로 보인다.

- **기존 방식**: LightGBM을 썼지만 결과가 만족스럽지 않았다.
- **파운데이션 모델**: ChatGPT처럼 대량의 데이터로 미리 학습을 마친 범용 모델이다. 여기에 회사 데이터로 추가 학습만 해도 더 높은 정확도로 예측했다.
- **외부 정보 추가**: 과거 인입량 시계열만으로는 예측이 되지 않았다. 그래서 강수량·휴일처럼 중요하다고 본 정보를 함께 넣었다.

핵심은 시계열 파운데이션 모델로 특정 시간대에 몰릴 문의와 문제를 미리 알아낸다는 것이다.

## D트랙 · 사내 바이브코딩 툴, 만들기 전에 따져 볼 것

사내 툴은 만드는 것보다 동료가 믿고 계속 쓰게 하는 게 더 어렵다는 이야기였다. 발표에서 짚은 문제는 여섯 가지다.

1. **나만 쓰기 쉽다**: 내게 편하면 끝이고, 다른 사람이 쓰기 어려운지는 고려조차 하지 않는다.
2. **웹앱이 꼭 필요하진 않다**: Claude 스킬 정도만 공유해도 끝날 문제라면 굳이 웹앱으로 배포해 공유할 이유가 없다.
3. **한 번 터지면 신뢰가 떨어진다**: AI로 만든 툴은 문제가 한 번 생기면 팀원들이 잘 믿어 주지 않는다. 전사 공유 전에 5명 정도로 베타 테스트를 해 오류를 줄이길 권했다.
4. **계속 알려야 한다**: 한 번 공유로는 부족하다. 발표자는 점심시간에 공유하는 식으로 꾸준히 알렸다.
5. **이미 있으면 만들지 말고 가져다 써라.**
6. **유지보수할 각오가 있을 때 만들어라**: 만들면 끝이 아니다.

'모킹버드'에서는 보안에 특히 신경 써서, 사내 계정으로 로그인하도록 했다.

**내 생각**

- 3번의 소수 인원 베타 테스트는 좋은 방법이지만, 회사 규모가 작으면 현실적으로 그대로 적용하기 어려워 보인다.

## D트랙 · AI로 전사 코드를 분석해 장애 원인 찾기

AI가 전사 코드를 직접 분석할 수 있게 되면서, 다른 팀 도움 없이도 장애 원인을 찾아 해결할 수 있게 됐다. 지금은 이런 흐름으로 돌아간다.

1. 슬랙 메시지 하나로 장애 조사를 시작한다.
2. 레이어마다 미리 만들어 둔 분석 코드로 조사를 실행한다.
3. LLM이 각 조사 결과를 읽고 판단한다.
4. 결과를 하나로 합쳐 최종 원인을 분석한다.

**겪은 문제와 대응**

- **엉뚱한 버그를 고친다**: A 버그로 장애가 났는데 AI가 B 버그를 고쳐 줬다. B도 논리적으로 문제 있는 코드였지만, 이번 장애와는 관련이 없었다. 그래서 이번 장애와 관련된 코드인지 검증하는 단계를 추가했다.
- **중요한 것부터 본다**: 경보에 우선순위를 미리 부여해, 더 중요한 부분부터 확인하게 했다.
- **팀별 조회 범위**: 배민은 팀이 커서 팀마다 조회할 수 있는 범위가 다르고, 전체 그림을 한 번에 보기 어려웠다.

**설계 원칙: 실행은 코드가, 판단은 LLM이**

- LLM에게 "트레이스 분석해"라고 그냥 맡기지 않는다. 트레이스 분석에 쓸 코드를 미리 만들어 두고 그것만 쓰게 한다.
- 목적은 실행 순서·방식·작업 시간을 정형화하는 것이다.
- 검증된 것만 추가 스킬로 반영하고, 나머지는 반영하지 않는다.

**내 생각**

- 팀별 조회 범위 문제는 배민처럼 큰 조직의 이야기다. 우리 회사 규모에서는 문제가 되지 않을 것 같다.

## E트랙 · B마트와 배민스토어, 퀵커머스 하나로 합치기

고객에게는 하나인 장보기 서비스가 회사 안에서는 공급자가 다른 두 서비스(B마트, 배민스토어)였다. 이 둘을 하나로 합치며 푼 문제들을 다뤘다.

퀵커머스는 재고를 고객 가까이에 두고 빠르게 배달하는 커머스를 말한다.

- **카탈로그 통합**: 용량처럼 빠져 있던 카탈로그 정보를 추가하고 통합했다.
- **지점별 가격**: 같은 상품도 지점마다 가격이 다르다(예: 송파 1,000원, 강남 500원). 셀러와 지점이 늘면서, 상품이 100개면 100건을 각각 고쳐야 하는 문제가 됐다.
    - **트랜잭션**: N건을 고치는 동안 커넥션을 끝까지 잡고 있으면 안 된다. 대신 차례대로 반영하면, 반영하는 동안 잠깐 값이 다르게 보일 수 있다.
    - **희소 오버라이드**: 지점 값이 본사 값과 같으면 지점 데이터를 따로 저장하지 않는다. 본사와 지점이 같은 값을 고치면 우선순위로 어느 값을 볼지 정한다.
- **조회용 재고 서비스**: 바이너리 RPC 통신과 인메모리 DB로 만들어 가볍고 빠르다.
- **전시 재고 매칭**: 두 서비스는 재고 관리 기준이 다르다. 예를 들어 배민스토어는 용량별 재고를 따로 관리하지 않는다. 이를 맞추려고 전시 재고 매칭 서비스를 만들었다.
- **조회와 주문의 DB 분리**: 상품 조회는 완벽하지 않아도 돼서 느슨하게 처리한다. 주문·결제는 정확해야 해서 원장을 조회한다.

## 마치며 · 가져갈 것

배민 같은 큰 조직의 고민도 있었지만, 아래 세 가지는 규모와 상관없이 바로 해 볼 수 있다.

- **스킬에 순서와 성공 기준 적기**: "잘 써 줘" 대신 무엇을 먼저 하고 무엇을 마지막에 점검할지, 어떤 기준을 넘겨야 하는지 적는다.
- **반복 작업은 코드로 고정하기**: 분석처럼 자주 하는 작업은 코드로 만들어 두고, LLM에는 판단만 맡긴다.
- **만들기 전에 따져 보기**: 사내 툴을 만들기 전에 이미 있는 도구는 없는지, 스킬 공유로 충분하지 않은지, 유지보수할 수 있는지부터 확인한다.
